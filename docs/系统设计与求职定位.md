# 系统设计与工程取舍

## 1. 项目究竟解决什么

Agent 应用通常把一个 API 模型接入工具就结束了，但这无法回答三个问题：

1. 小模型能否通过后训练稳定学会多轮状态与工具协议？
2. 模型什么时候应该调用、追问或停止，怎样被量化验证？
3. 模型输出不可信时，怎样防止未知工具、缺参调用和副作用动作越权？

本项目围绕这三个问题构建独立闭环。场景只负责提供可复现的输入和工具后端；技术主线是 Agent Trace、QLoRA、Tool Registry、Policy Engine、Guarded Runtime 与 Eval Harness。

## 2. 架构分层

```text
Data Plane
CrossWOZ → state normalisation → provenance → Agent Trace
                                              │
Model Plane                                   ▼
Gemma 3-1B ← 4bit QLoRA SFT ← prompt / JSON target
     │
     ▼
Control Plane
Contract → Tool Registry → Policy Engine → Local Executor
     │              │              │
  shape/type     allow-list      risk/required args
     │
     ▼
Evaluation Plane
Base-vs-QLoRA → test/challenge → scenario slices → error report
```

这四层可以分别替换：数据不必永远来自 CrossWOZ，模型不必永远是 Gemma，工具也可以换成真实 API；但输出契约、授权边界和评测口径仍然成立。

## 3. 为什么增加 Canonical Agent Trace

旧版每条数据只有 `history / previous_state / current_user / output`。它足够训练，却不容易表达“同一轮经过了哪些阶段”，也不利于未来迁移成标准 function-calling messages。

现在先用 `row_to_agent_trace` 统一为：

- `context`：历史、上一轮状态和当前输入；
- `tools`：从同一 Tool Registry 导出的 function schema；
- `events`：用户输入、模型目标、策略目标；
- `expected`：监督训练使用的结构化决策；
- `provenance`：自然样本或受控消融来源；
- `benchmark_tags`：指代、修正、跨领域等难例标签。

训练脚本再通过 `render_sft_pair` 渲染成与原实验一致的 Prompt/answer，因此这次重构不需要重新训练，也不会把旧指标错误地套到新目标上。

## 4. Tool Registry 为什么是单一事实源

每个工具统一声明：

- 名称和自然语言描述；
- 参数 JSON Schema；
- 领域；
- 必填参数；
- `read_only` 或 `side_effect` 风险；
- 执行器元数据。

Prompt、输出校验、Policy 和 OpenAI-compatible schema 导出都读取同一个 Registry，避免四处维护不一致。风险级别不接受模型输出，因此 Prompt Injection 或模型幻觉无法自行获得执行权限。

## 5. 模型与代码的职责边界

模型擅长：

- 从自然语言和历史中恢复语义状态；
- 在多个工具间选择；
- 生成候选参数；
- 判断当前是否缺少信息。

确定性代码负责：

- JSON 与字段类型；
- 工具白名单；
- 必填参数；
- 风险级别；
- 是否允许自动执行；
- 可审计运行事件。

核心原则是：**模型提议不等于执行授权。**

## 6. 后训练设计

Gemma 3-1B 以 4bit NF4 加载，冻结基础权重，只训练 Attention 与 FFN 投影层的 LoRA Adapter。Loss 仅覆盖目标 JSON；Prompt token 全部 mask 为 `-100`。

选择累计 `belief_state` 而非只预测 delta，是为了直接验证完整状态和减少运行时合并歧义。代价是长序列更难完全匹配，因此项目同时报告严格 JGA 与 Slot F1，并做状态长度分桶。

保留最近 6 轮是工程折中：它减少显存和无关历史，同时保留大部分指代和条件修正信息；这不是 Transformer 的理论上限。

## 7. Eval Harness 为什么分层

只报告“工具准确率”会掩盖很多失败：模型可能选对工具却输出非法 JSON，也可能参数错误，更可能在感谢语中不该调用却继续调用。因此评测分为：

- 格式：strict JSON、Schema；
- 状态：JGA、Slot P/R/F1；
- 决策：call / ask / no-tool；
- 工具：tool accuracy、argument exact、argument Slot F1；
- 安全：missing-argument ask、no-tool false positive、side-effect policy；
- 泛化：coreference、correction、cross-domain、long-state。

`BENCHMARK_REPORT.md` 按场景切片，`EXPERIMENT_REPORT.md` 保留总体对照、混淆矩阵、长度分桶和典型错误。二者都由逐样本预测自动生成。

## 8. 设计来源与本项目的映射

| 公开路线 | 借鉴点 | 本项目落地 |
| --- | --- | --- |
| BFCL | 格式、工具、参数、多轮分层评测 | Eval Harness 与 challenge slices |
| When2Call | 调用之外还要评估 ask/no-tool | 三分类决策与误调用率 |
| Open Trajectory Gym | Trace 贯穿数据、训练、评测 | Canonical Agent Trace |
| qwen35-agent-post-training | 社区后训练项目的模块化组织 | 数据/训练/策略/评测独立入口 |
| Llama3-FunctionCalling | 工具 Schema、LoRA、推理闭环 | Registry schema 与 QLoRA pipeline |

本项目没有声称复现上述官方榜单；它们提供问题拆分和工程组织的参考。

## 9. 为什么不继续加 RAG、MCP、前端或多 Agent

这些模块不会直接改善“工具决策是否可靠”这一研究问题，反而会稀释证据链。该项目刻意控制在一张白板能画清、每个指标可追溯、一个学生能够真正吃透的范围内。

如果后续扩展，优先级是：

1. 增加真实多工具顺序执行轨迹；
2. 增加更大规模的 no-tool / prompt-injection 安全集；
3. 对参数生成增加 constrained decoding 或 schema-guided decoding；
4. 在 SFT 基础上增加偏好优化，并用独立集验证；
5. 最后才是替换为真实 API 工具后端。

## 10. 诚实边界

- CrossWOZ 是公开任务型对话数据，不是企业线上流量；
- 受控缺参样本显式标记，不冒充自然样本；
- 本地 SQLite 只用于可复现执行；
- 打车不会真实下单；
- 当前一次只选择一个工具，不声称已经实现并行或多步工具规划；
- 参数 Exact Match 仍低，是下一版主要问题；
- challenge 不是 BFCL 官方成绩。

这些边界不会削弱项目，反而说明实验口径和工程授权是清楚的。
