# 系统设计与求职定位

## 为什么采用这条路线

第一项目 AgriAgent 展示的是应用层能力：规划、RAG、MCP、多 Agent 协作和完整业务流程。第二项目如果再做一个“换皮 Agent 应用”，关键词会重复，面试官也很难看到新的技术增量。

本项目向下走一层，回答三个更具体的问题：

1. 通用小模型怎样通过 QLoRA 学会稳定的工具调用协议？
2. 多轮对话中的状态变化、指代和缺参，怎样被固定数据和指标验证？
3. 模型输出不可信时，系统怎样保证未知工具、缺失参数和副作用动作不能越过边界？

因此两个项目形成互补：

| 项目 | 主要证明什么 |
| --- | --- |
| AgriAgent | 能设计完整 Agent 应用与业务工作流 |
| 本项目 | 能处理 Agent 的模型适配、上下文状态、评测和安全执行层 |

## 核心设计

### 1. 输入

每条输入由三部分组成：最近 6 轮历史、上一轮结构化状态、当前用户话语。保留上一轮状态的目的不是“堆一个 memory 关键词”，而是让模型明确学习状态增量：新约束要加入、修改约束要覆盖、指代要结合前文理解。

### 2. 模型输出

输出同时包含累计 `belief_state` 和本轮决策。选择累计状态而不是只输出 delta，便于直接计算联合状态准确率，也能在运行时完整校验；代价是序列略长，因此训练脚本保留完整答案、优先截断最早的 Prompt token。

### 3. 后训练

Gemma 3-1B 以 4bit NF4 加载，冻结基础权重，只训练 Attention 与 FFN 投影层上的 LoRA Adapter。Loss 仅计算目标 JSON，Prompt token 全部设为 `-100`。这样项目比较的是“通用 Base 模型”和“任务适配后模型”在同一协议上的差异。

### 4. 确定性策略层

模型不能决定工具是否安全。代码中的注册表固定记录：工具名、领域、必填参数和风险级别。

- 未注册工具：Schema 校验直接拒绝；
- 地铁/打车参数不完整：转成 `needs_input`；
- 景点/酒店/餐馆/地铁查询：只读并可自动执行；
- 打车：即使参数完整也只能进入 `pending_confirmation`。

把风险交给注册表而不是 Prompt，是为了避免模型幻觉或 Prompt Injection 改写系统授权。

### 5. 本地工具

参考数据被装入 SQLite。执行层只接受通过校验的 `ToolCall`，并且查询条件中出现数据库不存在的字段时返回 `not_found`，不会悄悄忽略未知字段后返回一堆错误结果。

### 6. 评测

评测拆成三层：

- 格式层：严格 JSON、Schema 合法率；
- 语义层：状态 JGA/槽位 F1、决策/工具/参数准确率；
- 安全层：缺参追问准确率、不该调用时的误调用率、副作用工具是否被策略拦截。

## 为什么没有继续加 RAG、MCP 和多 Agent

这些能力已经由第一项目展示。在第二项目里继续加入只会增加学习成本，并削弱“模型后训练 + 工具决策”这条证据链。本项目刻意不加入网页前端、复杂工作流、向量库和联网工具；面试时可以在三分钟内画完架构，也能沿任何一层深入解释。

## 可以诚实表述的成果

完成模型训练前，只能说已经完成数据管线、Schema/策略层、本地工具和自动测试。完成 Base-vs-QLoRA 全量评测后，再把真实指标补进 README 和简历。不能把 loss 下降等同于业务准确率，也不能把受控缺参样本说成真实企业数据。

## 当前工作名与简历命名原则

仓库暂用 `Gemma Tool-Use Lab`。最终简历标题不应只是罗列“Gemma、多轮、状态管理”三个技术词，而应概括交付物。建议等实测后从以下表达中择一：

- 面向任务型 Agent 的小模型工具学习与安全执行框架
- 轻量级大模型上下文工具决策与后训练系统
- Gemma 小模型工具调用后训练与可靠性评测

第一项最完整，第三项最克制。最终选择要与真实完成的指标和演示保持一致。
