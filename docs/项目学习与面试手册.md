# Gemma Tool-Use 从零学习路线与面试手册

这份手册分成两遍：

- **第一遍只求熟悉**：建立完整地图，知道每个模块为什么存在，能沿一条样本讲完输入、模型、策略、工具和评测。预计 8～10 小时。
- **第二遍面向面试**：补原理、代码细节、指标公式、设计取舍和失败分析。预计 20～30 小时，适合在第一遍完成后逐题训练。

不要从代码第一行背到最后一行。学习顺序始终是：**问题 → 数据 → 模型 → 协议 → 策略 → 工具 → 评测 → 边界**。

---

## 一、开始前先记住的项目答案

### 一句话版本

我基于 CrossWOZ 构造多轮状态与工具决策数据，使用 4bit QLoRA 对 Gemma 3-1B 做任务适配，使其根据对话历史维护 `belief_state`，并在调用工具、继续追问和无需工具之间决策；模型输出再经过 Schema、工具白名单、必填参数与风险策略校验，只有只读工具可以自动执行。

### 它的独立定位

这是一个完整的 Agent Tool-Use 后训练与可靠性项目：证明能够完成 Agent Trace 构造、QLoRA 后训练、上下文状态、工具协议、受控运行时和分层评测。它不依赖另一个项目才能成立，也不需要用 RAG、多 Agent 或网页前端制造工作量。

### 一条主链路

```text
最近对话 + 上一轮状态 + 当前输入 + 工具说明
                       ↓
                  Gemma 3-1B
                       ↓
 belief_state + decision + tool_call + missing_slots
                       ↓
     Schema → 工具白名单 → 必填参数 → 风险策略
                       ↓
      只读查询 / 继续追问 / 等待人工确认
```

### 已验证结果

训练配置：1,968 条训练样本、440 条验证样本，4bit NF4 QLoRA，训练 1 个 epoch。

| 指标 | Base test | QLoRA test | QLoRA challenge |
| --- | ---: | ---: | ---: |
| 严格 JSON 合法率 | 0.00% | 96.36% | 93.75% |
| Schema 合法率 | 2.50% | 98.41% | 98.75% |
| 状态 Slot F1 | 1.71% | 89.17% | 89.59% |
| 决策准确率 | 2.50% | 91.82% | 91.25% |
| 工具选择准确率 | 1.14% | 86.93% | 81.58% |
| 参数 Slot F1 | 0.00% | 68.63% | 59.61% |
| 参数完全匹配率 | 0.00% | 31.82% | 23.68% |
| 追问决策准确率 | 0.00% | 100.00% | 100.00% |
| 非工具轮误调用率 ↓ | 0.00%¹ | 11.36% | 9.52% |

¹ Base 几乎不能生成合法协议，因此没有产生有效工具调用；它的 0% 不能解释成更安全。

最重要的诚实结论是：**状态维护、决策与工具选择已经形成稳定能力，参数精确生成和长状态完全一致仍是弱项。**

## 二、第一遍：只求完整熟悉

第一遍不要钻公式，也不要重新训练。每一站控制在 60～90 分钟，达到“过关标准”就继续。

### 第 0 站：确认项目能运行

目标：知道项目不是一堆静态代码，当前环境、测试、Adapter 和报告都真实存在。

在项目根目录运行：

```powershell

.\run_local.ps1 -Mode analyze
.\run_local.ps1 -Mode benchmark
```

暂时不要运行 `train`、`eval-base` 或 `eval-qlora`，这些已经完成且耗时较长。

需要确认：

- 测试通过；
- `artifacts/tool_use_qlora_adapter/` 是训练得到的 Adapter，但被 Git 忽略；
- `reports/EXPERIMENT_REPORT.md` 是从三份原始评测输出自动生成的汇总证据；
- `.env`、Token、基础模型、Adapter 和逐样本原始输出都不会提交。

过关标准：能解释“代码、模型产物、原始报告、公开汇总报告”分别是什么。

### 第 1 站：先看最终功能，不看训练

目标：亲眼看到一次“模型 → 策略 → 工具”的完整运行。

```powershell
.\run_local.ps1 -Mode demo
```

运行时只观察四段内容：

1. 用户当前说了什么；
2. 模型输出了什么 JSON；
3. 策略层给出什么状态；
4. 工具是否执行以及返回什么。

你必须能区分三种结果：

| 决策 | 含义 | 系统行为 |
| --- | --- | --- |
| `call_tool` | 信息足够，需要外部能力 | 只读工具可以执行；副作用工具继续拦截 |
| `ask_user` | 缺少关键参数 | 不执行工具，要求用户补充 |
| `no_tool` | 致谢、确认或无需外部信息 | 不调用任何工具 |

过关标准：不看代码，能用自己的话解释三种决策有什么区别。

### 第 2 站：看懂一条数据

目标：理解模型到底吃进去什么、要学会输出什么。

打开 [`data/tool_use/test.jsonl`](../data/tool_use/test.jsonl)，只看第一条，不要连续阅读 440 条。认出六个字段：

- `sample_id`：样本编号；
- `history`：最近多轮对话；
- `previous_state`：上一轮已经确认的结构化状态；
- `current_user`：当前用户输入；
- `output`：监督训练目标；
- `source`：原始对话和构造来源。

重点理解 `output`：

```text
belief_state   到当前为止累计确认了什么
decision       当前应该调用、追问还是结束
tool_call      工具名与参数；非调用轮必须为 null
missing_slots  需要用户补充什么
```

需要自己回答：

1. 为什么只有当前一句话不够？
2. `previous_state` 和 `belief_state` 有什么区别？
3. 用户修改条件时，为什么输出累计状态而不是只输出变化量？
4. 为什么 `source` 和受控样本标记很重要？

过关标准：能拿一条 JSONL，从头指出输入和标准答案。

### 第 2.5 站：看懂 Agent Trace

目标：理解为什么项目不再只是“把几段文本拼成 Prompt”。

运行 `run_local.ps1 -Mode trace`，再打开 `artifacts/traces/train.jsonl` 第一条，依次认出 `context`、`tools`、`events`、`expected`、`provenance`。`traces.py` 把同一条标注同时供 SFT 渲染和离线审计使用；数据没有真实工具返回，因此 Trace 停在预期 Policy 结果，不伪造 `tool_response`。

过关标准：能解释“原始对话行、Canonical Trace、最终 SFT prompt/target”三者的关系。

### 第 3 站：看懂模型输出协议

目标：明白模型生成文本不等于系统可以相信它。

阅读顺序：

1. [`src/gemma_eval/tool_registry.py`](../src/gemma_eval/tool_registry.py) 的 `ToolSpec` 与 `DEFAULT_TOOL_REGISTRY`；
2. [`src/gemma_eval/contracts.py`](../src/gemma_eval/contracts.py) 的 `ToolCall`、`AgentDecision` 与 `validate_decision`；
3. [`src/gemma_eval/policy.py`](../src/gemma_eval/policy.py) 的 `apply_policy`；
4. [`src/gemma_eval/runtime.py`](../src/gemma_eval/runtime.py) 的 `AgentRuntime`。

先不要看 SQLite 查询实现。

要理解的四层边界：

- **Schema**：字段和类型是否合法；
- **白名单**：工具是否注册；
- **必填参数**：路线/打车是否有出发地与目的地；
- **风险策略**：只读查询可以自动执行，打车必须人工确认。

三个必须会解释的例子：

1. 模型输出 `run_shell`：白名单拒绝；
2. 模型请求打车但缺少目的地：转为 `needs_input`；
3. 模型提供完整打车参数：仍然是 `pending_confirmation`，不会真实派车。

过关标准：能回答“为什么不能只靠 Prompt 告诉模型要安全”。

### 第 4 站：看懂 Prompt 和多轮状态

目标：知道模型如何同时看到历史、状态和工具说明。

阅读 [`src/gemma_eval/tool_use_data.py`](../src/gemma_eval/tool_use_data.py)：

1. `SYSTEM_PROMPT`；
2. `tool_registry_prompt`；
3. `tool_use_prompt`；
4. `_state_items` 和 `_argument_items`。

要画出下面的数据流：

```text
history ───────────┐
previous_state ────┼─→ tool_use_prompt ─→ tokenizer ─→ Gemma
current_user ──────┤
tool registry ─────┘
```

需要自己回答：

- 为什么既给自然语言历史，又给结构化上一轮状态？
- 最近 6 轮是工程折中，不是模型理论限制，折中了什么？
- 为什么工具风险不写成让模型自由预测的字段？

过关标准：能说出 Prompt 的四部分及每部分作用。

### 第 5 站：看懂数据从哪里来

目标：证明自己不是下载一个 JSON 就直接训练。

阅读 [`scripts/build_tool_use_dataset.py`](../scripts/build_tool_use_dataset.py)，第一遍只看这些函数：

1. `normalise_user_state`：把 CrossWOZ 状态转成统一结构；
2. `build_rows`：把对话转成逐轮样本；
3. `balanced_sample` / `natural_sample`：控制训练与评测分布；
4. `controlled_missing_slot_examples`：补自然数据缺少的缺参安全样本；
5. `challenge_sample`：构造难例切片；
6. `write_reference_subset`：保存演示需要的本地参考数据。

必须记住数据规模：

- train：1,968；
- validation：440；
- test：440；
- challenge：80；
- test 与 train/validation 的 `sample_id` 无重叠。

关于受控缺参样本，标准说法是：

> CrossWOZ 中路线参数通常完整，无法充分检验缺参时是否会停下来，因此我使用各 split 内真实地点值做单槽位消融，并在 `source` 和 manifest 中显式标记。它是受控安全样本，不冒充自然企业数据。

过关标准：能解释数据来源、标签来源、为什么补缺参样本、如何避免数据泄漏。

### 第 6 站：看懂 QLoRA 训练

目标：知道“训练了什么”，不是只会背 QLoRA 三个字母。

阅读 [`scripts/train_tool_use_qlora.py`](../scripts/train_tool_use_qlora.py)，按下面顺序：

1. `encode_example`；
2. `ToolUseDataset`；
3. `CausalCollator`；
4. `BitsAndBytesConfig`；
5. `LoraConfig`；
6. `TrainingArguments`。

当前真实配置：

| 项目 | 配置 |
| --- | --- |
| 基座 | `google/gemma-3-1b-it` |
| 量化 | 4bit NF4、double quant、FP16 计算 |
| LoRA | `r=16`、`alpha=32`、`dropout=0.05` |
| 目标层 | Attention 的 q/k/v/o 与 FFN 的 gate/up/down |
| epoch | 1 |
| 学习率 | `2e-4` |
| micro batch | 1 |
| 梯度累积 | 8，有效 batch 约 8 |
| 最大长度 | 1,024 tokens |
| 随机种子 | 42 |
| 可训练参数 | 13,045,760，约占 1.29% |

必须理解三个实现细节：

1. **Base 权重冻结**：训练的是 LoRA Adapter，不是把 10 亿参数全部更新；
2. **Label mask**：Prompt token 的 label 是 `-100`，只对目标 JSON 计算 loss；
3. **截断策略**：序列过长时优先截断最早的 Prompt token，尽量保留完整答案。

真实训练结果：训练约 3 小时 17 分钟，`train_loss=0.1295`，`validation_loss=0.0357`。Loss 只能说明优化过程，不能代替最终任务指标。

过关标准：能回答“模型到底更新了哪些参数、对哪些 token 算 loss、为什么 6GB 显存能训练”。

### 第 7 站：看懂评测，不只挑好看的数字

目标：知道每个指标在测什么，也知道它没测什么。

阅读：

1. [`scripts/evaluate_tool_use.py`](../scripts/evaluate_tool_use.py)；
2. `tool_use_data.py` 的 `compare_decisions` 和 `aggregate_metrics`；
3. [`reports/EXPERIMENT_REPORT.md`](../reports/EXPERIMENT_REPORT.md)。

按三层理解指标：

| 层次 | 指标 | 说明 |
| --- | --- | --- |
| 格式 | strict JSON、Schema | 是否只输出 JSON，字段结构是否合法 |
| 状态 | JGA、Slot P/R/F1 | 累计状态是否完全/局部正确 |
| 行为 | decision、tool、arguments | 是否做了正确决策、选对工具、给对参数 |
| 安全 | ask-user、false positive | 缺参是否追问，不该调用时是否误调用 |

重点理解：

- JGA 是全有或全无；平均状态约 9.18 项，所以它会显著低于 Slot F1；
- 参数完全匹配要求整个工具调用一致，比参数 Slot F1 更严格；
- challenge 上状态和决策稳定，但参数 Slot F1 从 68.63% 降至 59.61%，说明参数泛化仍是短板；
- test 中 88 个非工具目标轮误调用 10 个，challenge 中 42 个非工具目标轮误调用 4 个，多数是“好的，谢谢”一类结束语。

过关标准：面对任意一个指标，能解释分母、判定条件和局限。

## 三、第二遍：面试深挖路线

第一遍结束后，再按以下七个模块详细学习。每个模块都要经历“原理讲解 → 代码定位 → 口述回答 → 追问反驳”。

### 模块 A：Transformer 与 Gemma 基础

要掌握：

- Token、Embedding、Decoder-only Transformer；
- Causal Mask、Q/K/V、Attention、FFN、残差；
- RMSNorm、RoPE、Sliding/Global Attention；
- Prefill、Decode、KV Cache；
- Logits、Greedy、Top-K、Top-P、Temperature。

掌握程度：能解释这些结构如何支持当前项目的自回归 JSON 生成，不要求推导所有公式。

### 模块 B：LoRA、量化与训练工程

要掌握：

- LoRA 的低秩增量 `ΔW = BA`；
- `r`、`alpha`、dropout 的作用；
- 4bit 量化为什么省显存，计算为何仍使用 FP16；
- NF4、double quant、gradient checkpointing；
- micro batch、梯度累积、有效 batch；
- label mask、teacher forcing、训练/验证 loss；
- 为什么不能用 loss 代替任务准确率。

代码锚点：`train_tool_use_qlora.py` 第 23～46、110～159 行附近。

### 模块 C：多轮状态与数据构建

要掌握：

- Belief State 是什么；
- previous state、current state、delta state 的区别；
- 指代、约束追加、约束修改、跨领域切换；
- CrossWOZ 的原始标注如何映射到本项目协议；
- 分层抽样、自然分布、challenge、controlled ablation；
- 数据泄漏、标签噪声和样本 provenance。

必须能回答：“参数完全匹配率低，到底是模型问题还是标签问题？”正确答案是两者都有，需要用失败样例拆分，不能简单怪评测器。

### 模块 D：工具调用协议与安全执行

要掌握：

- Function Calling / Tool Use 的本质；
- Schema 验证和 tolerant parsing 的区别；
- 为什么模型提议不等于执行授权；
- 工具白名单、必填参数、风险分级、人工确认；
- Prompt Injection 为什么不能改变代码中的权限；
- 只读工具与副作用工具的不同失败后果；
- 为什么 SQLite 只是可复现工具后端，不是项目核心。

代码锚点：`contracts.py → policy.py → local_tools.py → runtime.py`。

### 模块 E：评测、对照实验与错误分析

要掌握：

- 为什么 Base 和 QLoRA 必须同模型、同 Prompt、同数据、同精度、同解码；
- Precision、Recall、F1；
- JGA 为什么随状态长度下降；
- 决策混淆矩阵如何看；
- Exact Match 与 Slot F1 为什么都要保留；
- 非工具误调用率为什么属于安全指标；
- test 与 challenge 各自证明什么；
- 如何从失败样例提出下一版改进，而不是盲目增加 epoch。

当前主要错误：

1. 长状态中漏掉或多出一个槽位；
2. 选对工具但参数不完全一致；
3. 感谢/结束轮仍继续调用工具；
4. 极长输出重复列表，导致严格 JSON 失败。

### 模块 F：项目设计取舍

至少准备下面问题：

1. 为什么选 Gemma 3-1B，不选 API 大模型？
2. 为什么不是 Prompt Engineering？
3. 为什么训练累计状态，不训练增量状态？
4. 为什么保留最近 6 轮？
5. 为什么不使用 LangChain/LangGraph？
6. 为什么 Tool-Use 后训练项目不加 RAG、MCP、多 Agent？
7. 为什么风险等级放代码注册表，不让模型决定？
8. 参数完全匹配率不高，这个项目还有什么价值？
9. 如果上线，下一步首先改什么？
10. 如何监控线上工具误调用和状态漂移？

所有答案都要围绕真实实现和指标，不能用“企业级”“生产可用”之类空话。

### 模块 G：简历与模拟面试

- 30 秒、1 分钟、3 分钟项目介绍；
