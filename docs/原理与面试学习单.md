# Gemma 推理与评测：零基础学习单

这份文件不是让你背诵代码，而是帮助你把项目讲成一条完整、真实的技术故事。每一部分都必须满足三个层次：知道它解决什么问题、能指出对应代码、能解释实验结果。

## 1. 这个项目到底在解决什么问题

大模型加载成功并不等于可以部署。真正落地时至少要回答：

- 模型怎样一步一步生成 token？
- 为什么输入越长、输出越长，推理会越来越慢？
- KV Cache 用额外显存换取了什么？
- 4 位量化到底节省了多少显存，会不会变慢或答错更多？
- 不同方案是否在相同条件下测试，结果能不能复现？

项目的任务就是用 Gemma 3 1B-it 把这些问题变成代码和实验，而不是只复述概念。

## 2. 必须讲懂的五个概念

### Token 与自回归生成

模型不是一次写出整句话，而是根据已有 token 预测下一个 token 的概率。选出一个 token 后，把它接回输入，再预测下一步，直到遇到结束符或达到长度上限。这就是自回归。

你要能在 `src/gemma_eval/decoding.py` 中指出循环、logits 和新 token 拼接的位置。

### Logits、Softmax、Top-K 与 Top-P

Logits 是模型对词表中每个候选 token 给出的原始分数。Softmax 把分数变成概率。

- Top-K：每一步只保留分数最高的 K 个候选；
- Top-P：按概率从高到低累加，只保留累计概率刚好覆盖 P 的候选集合；
- Temperature：改变概率分布的尖锐程度；越低通常越保守。

你要能解释：Top-K 的候选数固定，Top-P 的候选数会随当前概率分布改变。

### KV Cache

注意力计算需要历史 token 对应的 Key 和 Value。没有 Cache 时，每生成一个新 token，都要重新计算整段历史；启用 Cache 后保存历史 K/V，下一步通常只计算最新 token。

它不是“免费加速”：Cache 会占用显存，而且序列越长占用越大。项目比较的是相同模型、提示词和输出长度下，有无 Cache 的解码吞吐差异。

### 量化

量化用更低位数表示模型权重。例如从 16 位降到 4 位，通常可以明显降低模型内存，但不保证在所有 GPU 上都更快，也可能影响输出质量。

本项目只做推理量化，不训练模型，也不声称设计了新的量化算法。

### TTFT、TPS 与峰值显存

- TTFT（Time To First Token）：从开始推理到产生第一个新 token 的时间，主要受提示词 prefill 影响；
- Decode TPS：产生第一个 token 后，后续每秒能生成多少 token；
- Total TPS：把 prefill 也算进去的端到端吞吐量；
- Peak Memory：本次实验期间观察到的峰值显存。

不能只说“速度提升”，必须说明是 TTFT、Decode TPS 还是端到端时间。

## 3. 三个核心实验

### 实验 A：手写解码正确性

固定模型、输入和贪心策略，比较手写循环与 Hugging Face `generate` 的新 token 序列是否完全一致。

如果不一致，先排查聊天模板、停止 token、attention mask、Cache 更新和精度，而不是继续做性能结论。

### 实验 B：KV Cache 消融

只改变 `use_cache`，其余条件保持相同。记录 TTFT、Decode TPS、Total TPS 和峰值显存。

预期不是提前写好的答案。合理现象可能是 Cache 提高后续 token 吞吐，同时增加缓存内存；具体幅度由实测决定。

### 实验 C：16 位与 4 位对比

两种精度分开加载和运行，避免两个模型同时占用显存。除了性能和内存，还要在同一固定题集上比较通过率，并阅读失败样例。

若 4 位更省内存但速度没有提升，这也是有效结论，不能删除。

## 4. 面试时最容易被追问的地方

1. 为什么手写解码还要和 `generate` 对齐？
2. 为什么测试前需要预热和 CUDA 同步？
3. 为什么 TTFT 和 Decode TPS 要分开？
4. 有 Cache 为什么仍要传递完整 attention mask？
5. 4 位量化为什么不一定更快？
6. 固定题集通过率能否代表模型整体能力？
7. 为什么只报告中位数，还需要保留每轮原始结果吗？
8. 如果换一张 GPU，原来的性能结论还能直接使用吗？

每个问题的回答都应落到本项目的代码和实验，而不是泛泛背定义。
